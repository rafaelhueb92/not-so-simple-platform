# GitOps Platform Demo

Minimal infrastructure demo showing:

- Containerized FastAPI app with metrics
- Kubernetes manifests + GitOps (ArgoCD Application)
- Local dev with kind
- Terraform EKS module caller
- Monitoring: local Prometheus + AWS Managed stubs
- CI with GitHub Actions (plan-only)
- IAM/Security: OIDC, ECR read, IRSA-ready

## Quickstart

1. Run `./scripts/kind-create.sh`
2. Run `./scripts/load-image.sh`
3. Run `./scripts/kind-label-taint.sh`
4. Run `./scripts/deploy-local.sh`
5. Optional: `./scripts/deploy-monitoring-local.sh`

See `docs/walkthrough.md` for a guided tour.

## Monitoring

The cluster runs the [`kube-prometheus-stack`](https://github.com/prometheus-community/helm-charts/tree/main/charts/kube-prometheus-stack)
Helm chart — Prometheus, Grafana, Alertmanager, node-exporter, and
kube-state-metrics — installed by `dev/init.sh`.

### Dedicated node

The stack is pinned to a node dedicated to monitoring, using the same
taint + toleration + nodeSelector pattern as the ArgoCD node:

- **Taint** `dedicated=monitoring:NoSchedule` repels all other workloads.
- **Toleration** + **nodeSelector** `dedicated=monitoring` pin Prometheus,
  Grafana, Alertmanager, the operator, and kube-state-metrics onto it.
- **node-exporter** is exempt — it's a DaemonSet and tolerates all taints so it
  scrapes every node.

Provisioning of the node itself is per-environment (the Helm values are portable):

| Env | Where the node comes from |
|-----|---------------------------|
| KIND (dev) | `dev/kind-config.yaml` — a worker with `register-with-taints` + `node-labels` |
| EKS (prod) | `infra/eks/monitoring-nodegroup.yaml` — a managed node group with matching `labels` + `taints` |

Config: `dev/prometheus-values.yaml`.

### Accessing Grafana

```bash
kubectl -n monitoring port-forward svc/kube-prometheus-grafana 3000:80
# open http://localhost:3000
# user: admin   password: see ./secret-grafana.txt (generated by dev/init.sh)
```

The **Hello App Metrics** dashboard (`app/dashboards/hello-dashboard.json`) is
auto-loaded via the Grafana dashboard sidecar: `dev/init.sh` creates a ConfigMap
labelled `grafana_dashboard=1` in the `monitoring` namespace, and the sidecar
imports it (no restart / manual import needed).

### Accessing Prometheus

```bash
kubectl -n monitoring port-forward svc/kube-prometheus-kube-prome-prometheus 9090
# http://localhost:9090/targets   -> confirm hello-servicemonitor is UP
# http://localhost:9090/graph     -> query e.g. rate(hello_requests_total[5m])
```

### How app metrics get scraped

1. The app exposes Prometheus metrics at `/metrics` (`hello_requests_total`).
2. `app/manifest/servicemonitor.yaml` selects the `hello-service` (label
   `app: hello`) and scrapes its named `http` port every 15s.
3. Prometheus discovers the ServiceMonitor because the values set
   `serviceMonitorSelectorNilUsesHelmValues: false` (otherwise only
   `release`-labelled monitors are picked up).

Generate some traffic so the graphs move:

```bash
for i in (seq 50); curl -s http://localhost/ > /dev/null; end   # fish
```

### Verify placement

```bash
# monitoring pods on the dedicated node; nothing else there
kubectl -n monitoring get pods -o wide
kubectl get pods -A -o wide \
  --field-selector spec.nodeName=not-so-simple-platform-cluster-dev-worker4

# node-exporter runs on ALL nodes
kubectl -n monitoring get pods -l app.kubernetes.io/name=prometheus-node-exporter -o wide
```
